# Semantic occurrence correlation contract

This contract defines the repository-owned boundary between schema-v1 semantic
facts and a syntax consumer's response-local node IDs. The reference
implementation is `internal/occurrencemap`; JSON fixtures under
`internal/occurrencemap/testdata/v1` are the language-neutral conformance data.

The repository does not contain an OXC parser or Rust package. A production
OXC adapter must walk its AST, project each relevant `NodeId` into the node
candidate records below, and keep the returned mapping in a response-local side
table. It must not persist `NodeId` values or add them to the semantic-facts
producer protocol.

## Identity and indexing

Both facts and node candidates use normalized project-relative file names and
zero-based, half-open UTF-8 byte spans. A correlation key is:

```text
(file, start, end, semantic-facts syntax kind)
```

The consumer builds two indexes:

1. canonical node identities, for exact matches;
2. explicitly declared alternative anchors, for known parser-boundary or kind
   differences.

Canonical identity lookup is a hash-table lookup in the reference
implementation. Building the indexes is O(nodes + anchors), and correlating a
fact performs at most one exact lookup and one normalized lookup. There is no
linear AST scan or containment fallback. A tree-based implementation may use
O(log n) lookups while preserving the same result.

The input node ID is an opaque unsigned integer scoped to one file's syntax
arena. The same numeric ID may occur in another file. Its only meaning is the
consumer's response-local syntax node; ordering and persistence never convey
identity.

## Syntax-kind projection

`syntaxKind` on a successful canonical or normalized key uses the schema-v1
TypeScript spelling, such as `KindIdentifier` or `KindStringLiteral`. An OXC
adapter projects parser variants by semantic role instead of comparing raw enum
numbers. The initial crosswalk is:

| Semantic-facts kind | Consumer syntax roles |
| --- | --- |
| `KindIdentifier` | reference, binding, property-name, and JSX-name identifiers |
| `KindPrivateIdentifier` | private identifiers |
| `KindStringLiteral` | string literals, directives, and quoted JSX attribute values |
| `KindNumericLiteral` / `KindBigIntLiteral` | numeric and bigint literals |
| `KindNoSubstitutionTemplateLiteral` and template token kinds | the corresponding template token or quasi |
| keyword expression/type kinds | the corresponding keyword token or semantic carrier node |

The adapter may emit a `kind-alias` anchor when its canonical node label is more
specific. It must not collapse two different nodes merely because they project
to the same semantic-facts kind; that produces a multiply-mapped diagnostic.

## Normalization rules

Every alternative anchor names one of three closed rules. The reference
implementation validates the span relationship before indexing it.

- `kind-alias`: the byte span is identical, but the parser-side kind is
  projected to the semantic-facts kind.
- `protocol-inner-span`: the semantic-facts anchor is a proper subspan of the
  canonical consumer node. This covers a token occurrence whose syntax parser
  exposes only a semantic carrier node around it.
- `protocol-outer-span`: the semantic-facts anchor properly contains the
  canonical consumer node. This covers delimiter ownership differences, such
  as a quoted JSX attribute value whose consumer node records only its content.

Alternative anchors are allow-listed by the consumer adapter. They are not
generated by trying every parent, child, or containing span. A new boundary
shape requires a fixture and either one of the existing relationships or a new
contract version.

## Match and ambiguity behavior

For every fact, the correlator applies this fixed order:

1. If exactly one canonical candidate has the exact key, map it as `exact`.
2. If several canonical candidates have the exact key, emit `multiply-mapped`
   and do not attach the fact. Normalized candidates are not consulted.
3. Otherwise, if exactly one distinct node has a declared alternative anchor,
   map it as `normalized` and report the rule.
4. If several distinct nodes have alternative anchors, emit
   `multiply-mapped` and do not attach the fact.
5. If neither index has a candidate, emit `unmapped`.

Candidate IDs in diagnostics are sorted numerically. If one node declares the
same anchor more than once, it remains one candidate and the lexically first
rule is reported. Facts, mappings, and diagnostics retain fact order; coverage
rows are sorted by semantic-facts syntax kind. Node traversal order therefore
cannot affect the report.

Ambiguous occurrences are intentionally not resolved by choosing the lowest
`NodeId`, nearest ancestor, or first traversal result. Such choices are stable
only accidentally and can silently attach semantics to the wrong node.

## Coverage report

The report includes aggregate `summary` counts and `bySyntaxKind` rows. Each
metrics object contains:

```json
{
  "facts": 3,
  "mapped": 2,
  "exact": 1,
  "normalized": 1,
  "unmapped": 0,
  "multiplyMapped": 1
}
```

`mapped` is exactly `exact + normalized`, and every fact contributes to exactly
one of `exact`, `normalized`, `unmapped`, or `multiplyMapped`. Consumers can
derive ratios without relying on floating-point serialization. The v1 fixtures
cover JSX, declarations, expressions, flow-sensitive occurrences, exact-match
precedence, both diagnostic states, and input-order determinism.

## Missing production boundary

Completing an actual OXC integration requires a Rust-owned adapter with access
to the OXC AST and its arena-local `NodeId`s. That adapter must:

1. produce candidates and allow-listed anchors from an OXC traversal;
2. run these fixtures against its implementation of this contract;
3. measure real-project coverage by syntax kind; and
4. store successful mappings in an OXC-side table.

None of those operations can be implemented faithfully in this Go repository
without adding a second parser or fabricating foreign node IDs. The portable
contract, reference algorithm, diagnostics, metrics, and fixtures are the
smallest useful work that belongs here.
